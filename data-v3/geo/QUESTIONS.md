# Geo & Institution Data lane: answers to Q-G1 to Q-G7

Answers to `docs/v3/DATA_LOADING.md` §10 (branch `v3/plan`, 973c96c). State of branch `data/geo` on Oct 18, 2026.
Each answer separates **Done** (committed on `data/geo`, with the commit) from **Planned** (not built yet; nothing
here should be loaded until it is listed as done). Counts are from the files on `data/geo` at a9deb5f.

## Decided by the orchestrator (Oct 18, 2026, 06:08 EDT)
These decisions replace the "proposal" / "recommendation" parts of the answers below:
- **Q-G2 format: decided.** Geometry ships as GeoJSON, one file per layer × vintage (`data-v3/geo/<layer>_<vintage>.geojson`). Any file over about 5 MB is gzipped (`.geojson.gz`), or kept out of git and regenerated by a build script in `tools/`.
- **Q-G3 full resolution: decided.** Full-resolution TIGER stays out of git. v3 fetches TIGER/Line from census.gov and joins on the `geoid` in these tables.
- **Q-G5 towns: decided.** TIGER county subdivisions (cousub, GEOID SSCCCMMMMM) are the canonical town layer.
- **Q-G6 institutions: decided.** `data-v3/geo/entities.csv` is approved (not built yet).
- **Q-G7 precincts: decided.** Per-year precinct IDs, plus a 2020→2024 area crosswalk table, are approved (not built yet).
Q-G1 (done) and Q-G4 (recommendation: three school unit types) are unchanged by these decisions.

## Q-G2: format of data-v3/geo
**Done:** attribute tables only. UTF-8 CSV with a header and one file per layer, all TIGER **2024** vintage (the vintage is
fixed for every file today; a future vintage would get its own file, e.g. `schools_2026.csv`). Format details are in `README.md`. No geometry is in
`data-v3/geo/` yet. The geometry v3 can read today is the v2 encoding (÷1000 national, ÷10000 per state and parts),
with lon/lat in EPSG:4269 (NAD83, TIGER's native CRS; it differs from EPSG:4326 by less than 1 m, and v2 does not reproject).
**Planned (proposal; the orchestrator has not decided yet):** geometry as GeoJSON keyed by `geoid`, one file per layer × vintage
(`data-v3/geo/<layer>_2024.geojson`), properties `geoid, name, state_fips, tiger_set`, coordinates EPSG:4326 rounded to 6 decimals.
GeoJSON was chosen because the repo is plain git with GitHub Pages and the v3 loader already parses GeoJSON. FlatGeobuf or GeoPackage would only be used if v3 asks.

## Q-G3: full-resolution TIGER
**Done:** nothing full-resolution is committed. The untouched raw TIGER 2024 shapefiles used so far are on the box,
outside the repo: `/workspace/w/lanes/geo-data-raw/tiger2024/tl_2024_19_cousub.zip`, `tl_2024_40_elsd.zip` and `tl_2024_40_unsd.zip`. The Gazetteer files are in `/workspace/w/tiger/`.
**Planned:** this lane will **not** commit full-resolution national TIGER to git, because the national shapefiles are hundreds of MB.
For point-in-polygon accuracy v3 should load TIGER/Line 2024 itself from `https://www2.census.gov/geo/tiger/TIGER2024/<LAYER>/`
(public domain), and join it on the `geoid` in these CSVs. The lane can provide a fetch script `tools/fetch_tiger.py`
(URL list + sha256 manifest, `data-v3/geo/tiger_manifest.csv`) on request. Simplified display geometry (the proposal under Q-G2) would be
lod-style: districts at 0.0005° on shared arcs, the same method as the Iowa townships in a9deb5f (no gaps or overlaps between neighbours).

## Q-G4: school district types
**Done:** each school row already carries its TIGER type in `schools.csv` `tiger_set` (`unsd` 10,872, `elsd` 1,952, `scsd` 481).
Elementary and secondary districts do overlap: a point in an ELSD state can lie in one elsd and one scsd row (for example
CA, IL, AZ, MT). Oklahoma's 96 added elementary districts (a6e4360) do not overlap any Oklahoma unified district; this was checked.
**Recommendation:** three v3 unit types `school_unified`, `school_elementary` and `school_secondary`, mapped 1:1 from `tiger_set`, and allow
several school units per point. A single `school` type would lose which board a voter elects.

## Q-G5: canonical town layer
**Done / fact:** the three are different things. `data/<State>.js` `towns` are county subdivisions (v1, ÷10000).
`places` are incorporated places and CDPs (they are not county subdivisions). `v2/data/parts/<State>.js` rows are `[county, town, polys|null]`,
the county-part of a town (null = use the v1 geometry). The Iowa townships (3ec03fb, re-simplified in a9deb5f) are **new**
TIGER FUNCSTAT-G county subdivisions placed in `parts/Iowa.js` (1,598 rows), keyed `county|name`, with GEOIDs in `towns.csv`.
**Recommendation:** the canonical v3 county-subdivision layer is TIGER `cousub` keyed by GEOID (SSCCCMMMMM). v1 `towns` and `parts` rows
map onto it; `places` stays a separate `place` layer. The Iowa townships use the same `county|name` key as other parts rows, plus a GEOID.

## Q-G7: stable precinct IDs by year
**Done:** nothing in `data-v3/geo/`. Precinct geometry stays embedded in `data/precincts2020|2024/*.js` (root `data/`, read-only
for this lane). Today the only key is the v2 `County|Precinct` name, and it is **not unique**. Repeated (county, name) rows:
2024: North Carolina 7, Pennsylvania 1; 2020: Massachusetts 1,918, Oklahoma 556, Pennsylvania 51, Arizona 4, North Carolina 2,
Georgia 1, New Mexico 1. The source datasets (VEST, state files) also have their own precinct codes, but v2 does not keep them.
**Planned (proposal):** `data-v3/geo/precincts_<year>.csv` with `precinct_id = <USPS>-<year>-<county FIPS>-<row ordinal in the v2 file>`, plus
`county, v2_name, source_id` (VEST/official code where it can be recovered) and a centroid. The ID would be stable for a given year
and source file. Precincts are not stable across years, so a 2020↔2024 link would be an area crosswalk table, not shared IDs.

## Q-G8: duplicate place and town keys (from v3, Oct 18, 2026)

**Answer: 8 v2 rows renamed; 16 left alone because the app already hides them; 1 town key can't be fixed in v2.** Done with `tools/fix_dup_place_keys.py`.

**Places.** Root `data/<State>.js` has 11 place names used twice in one state, 22 v1 rows in all:
- MN: St. Anthony city.
- OH: Oakwood village.
- PA: Coaldale, Newburg, Liberty, Centerville, Pleasantville and Jefferson boroughs.
- TX: Reno city, Oak Ridge town and Lakeside town.

24 rows in `v2/data/parts/` carry these names. The v1 rows stay as they are (root `data/` is read-only).

A parts row with no geometry borrows the v1 place polygon by (state, name), and the app takes the first match. So a second county could show the other place's shape and figures.

**What was wrong before:**
- TX Kaufman County's Oak Ridge town showed Cooke County's Oak Ridge.
- TX Tarrant County's Lakeside town showed San Patricio County's Lakeside.

**Renamed (8 rows), using the school convention "Name (County)", with "County" dropped like the school rows:**
- OH: Oakwood village (Paulding).
- TX: Reno city (Lamar), (Tarrant) and (Parker); Oak Ridge town (Cooke) and (Kaufman); Lakeside town (San Patricio) and (Tarrant).
- Every renamed row that had no geometry now carries, verbatim, the v1 polygon of the same-named place in its own county.
- All 8 are added to `v2_name_collisions.csv` with their TIGER 2024 place GEOID. For these rows, `row` is the index in `v2/data/parts/<State>.js`.

**Left alone (16 rows): every MN and PA row, and OH Cuyahoga.** In each case a v1 town row of the same county with the same normT() name shows the right polygon, so the parts row is hidden. Renaming it would un-hide it and show the town twice. These keys don't break lookups in v2.

**Towns.** There is one duplicate v1 town key (2 rows): Ohio, Union County, "Washington township". These are two different TIGER county subdivisions:
- 3915981662: FUNCSTAT A, 27.7 sq mi.
- 3915981242: FUNCSTAT C, 1.9 sq mi.

Both rows are v1 (`data/Ohio.js`) and the app always shows v1 town rows. A rename can't be done in v2 without editing root data or `index.html`, so it is left for the orchestrator's move off v1. The fix would be to rename the second row "Washington township (3915981242)" or give it a county-unique label.

**Towns added in this pass:** every new parts row gets a (county, name) that is unique in its file, and a (state, name) not already used by a v1 place. The fill tool checks this before writing.

## Q-G9: town file size, 300 KB target (ruled by the orchestrator, Oct 18, 2026)

Ruling: (a) keep v2/data/parts/ and places/ at coverage-simplification tolerance 0.002° (about 100-200 m median deviation)
as built. GitHub Pages serves .js gzipped (the big-state parts files are 130-290 KB gzipped), so v2 gets no format change.
The per-state size tables (raw and gzip at each tolerance) are in the build reports of tools/build_town_files.py.

v3 note (not done in v2): per-row overhead (county name, town name, first absolute point, about 60 bytes) is a large share of a
parts file (about 150 KB in Pennsylvania). A v3 town format could
- store a county index (`counties:[...]` once, rows `[countyIndex, name, enc]`), or split files per county and load them lazily;
- let a parts row of an incorporated place reference its places/ row instead of repeating the clipped geometry when the place lies
  in one county (about half of the Texas parts bytes);
- store shared arcs once (TopoJSON-style), since the coverage simplification already makes neighbouring rows share identical
  vertices.

## Q-G11: Canada 2021 layers (Oct 18, 2026), open points

Built: `ca_pr` 13, `ca_cd` 293, `ca_csd` 5,161, `ca_fed2013` 338, `ca_fed2023` 343 (CSVs in git, GeoJSON in `../geo-data-raw/v3ca`,
see README "Canada, Statistics Canada 2021"). All counts equal StatCan's and Elections Canada's published totals, per province.

1. **v2/data/canada.js vs the new layers.** `canada.js` (77,739 B) is Natural Earth 1:50m admin-1 (public domain), 13 rows
   `[name, code, S, W, N, E, rings]` with about 5,000 vertices in total (Nunavut 79 rings / 2,652 points, Saskatchewan 6 points). The app
   uses it for the Canada map overlay, click hit-test, province silhouettes in lists and the "Province" geo-search entries. It is
   not derived from StatCan and does not nest with CD/CSD. `ca_pr` is the StatCan replacement for v3 (≈ 2.5 M vertices at 50 m).
   Join on the code, not the name: canada.js says "Québec", `ca_pr.name_en` "Quebec" (`name_fr` "Québec"). Code → `pruid`:
   NL 10, PE 11, NS 12, NB 13, QC 24, ON 35, MB 46, SK 47, AB 48, BC 59, YT 60, NT 61, NU 62. No change made to canada.js (v2 is
   not touched by this build); a v2 swap would need a display tier (point 2).
2. **Why `ca_pr_2021.geojson.gz` is 14.8 MB for 13 features (52.9 MB raw).** It is coastline and islands: 175,787 polygon parts and
   2,485,462 vertices; 155,127 parts (88 %) are tiny islands of ≤ 8 vertices. Nunavut alone is 62,552 parts / 1,126,340 vertices
   (45 %); B.C., Ontario, Newfoundland and Labrador and Quebec are 250-305 k vertices each; Saskatchewan and Alberta (no sea coast)
   are 833 and 2,779 vertices. CD is the same story (176,212 parts, 2.64 M vertices). PR and CD are by design the exact unions of the
   50 m CSDs, so they keep every CSD island.
   **Recommendation:** keep the 50 m PR/CD as the analysis/nesting layers (shared edges with CSDs). A coarser tolerance on PR/CD
   alone would break that nesting, so do not re-simplify them in place. For display at country/province zoom, add a separate
   derived tier (e.g. `ca_pr_2021_lo`, `ca_cd_2021_lo`: coverage_simplify of the PR/CD coverage at ≈ 500-1,000 m and dropping parts
   under ≈ 1-5 km²), sized like canada.js. Not built; needs the orchestrator's choice of target size or zoom range.
   **Decision (Full Stack, cc orchestrator, Oct 18, 2026): closed.** No separate low-detail tier; the v3 PMTiles build simplifies
   per zoom level, so keep shipping full-resolution official geometry (as in fdae0c3).
3. **Server-side failures.** StatCan's REST service returned HTTP 500 for three features on every full-resolution request (again
   on Oct 18, 2026); the www12 zip downloads return 403 to scripts. Used instead: CSD 6204030 (Qikiqtaaluk, Unorganized) and FED 59028
   (Skeena--Bulkley Valley) at 10 m server generalization; FED 62001 (Nunavut) = union of Nunavut CSDs. If the CBF zips become
   reachable (browser download), rebuild with those three at full resolution; nothing else changes.
4. **FED 2023 names.** The Elections Canada file (zip dated 2026-09-03) is used as published; open.canada.ca notes 17 names were
   updated by Bill C-25 (2026). Not checked against the Act; names can change again in place, so key on `fed_num`.
5. **FED 2013 → 2023.** `ca_fed2013_2023.csv`: 691 overlapping pairs (≥ 0.1 % of either), 89 same-number pairs, 74 pairs where each
   covers ≥ 99 % of the other. Elections Canada says 48 districts are unchanged; our 74 is an area test (it counts small
   boundary adjustments and the 3 territories as "same"), not a legal-description comparison.
6. **Institutions alignment hooks:** PR ↔ provincial governments (`pruid`), CD ↔ counties / regional municipalities / MRCs
   (`cduid`), CSD ↔ municipalities and First Nations reserves (`csduid`, `type` = CSD type such as CY, T, MÉ, RM, IRI), FED ↔ MPs.
