## Alpha.1 engineering calls (2026-10-18)

These are not new product decisions. They record what the first build did where the plan was silent.

- The shell is vanilla TypeScript (D1a without React). MapLibre and the list call `/api/v1`. `%` / `#` re-sorts with `packages/core` and does not refetch.
- Runtime DDL is `v3/db/migrations/`. Each file's checksum is stored in `usd.schema_migration`. Reference rows are `v3/db/seed.sql` and can be applied again. `docs/v3/SCHEMA.sql` remains the design document. Apply fixes are in SCHEMA.md (public tenant seed, `data_version`).
- `unit` is the Census GEOID. The v2 name is `legacy`. One contest on `/results` is the flat shape in API.md. Several contests use `series`.
- Official rows supersede `v2_import` for the same contest and unit (history kept), so a v2 `other` bucket is not added to official third parties.
- `dem_nominee` / `rep_nominee` only when that party has one candidate. Otherwise the key is `cand:<id>`.
- R02–R10 run in TypeScript and land in `stg_reject`. R12–R14 wait for alpha.2. Materialized views refresh inside the load transaction (not `CONCURRENTLY`).
- The dev role is a superuser. A read-only role stays the production plan. No connection string is stored in the repo. `db:migrate`, `db:seed`, and `db:load` read `DATABASE_URL` at runtime. A `neon.tech` host uses `@neondatabase/serverless` over WebSocket, because TCP 5432 is blocked where those commands run. Any other host uses `pg` on TCP. Tests refuse a Neon host. The user's free Neon project is `ultrevote` (database `neondb`, PostGIS 3.6). Loads batch with `jsonb_to_recordset` (no COPY on the WebSocket driver), skip a file whose sha is already applied or rejected, and bump `data_version` when rows change. Staging rows are deleted before commit. Unlogged staging tables on Neon also vanish when the compute suspends.
- State polygons come from `v2/data` (÷1000). `data/geo` has no state polygon file. Alpha.2 loads `v2-2024` state, county, and congressional units with those polygons, plus state-legislative and school units from `data/geo` (no polygons). Companies, institutions, governments, seating, and people stay behind flags. Company locations add `entity_location.country_code` and a clustered PMTiles archive plus `/api/v1/locations`. The style points at PMTiles and falls back to GeoJSON states.
- Alpha.3 keeps precinct facts out of Postgres on purpose. Polygons come from `v2/data/precincts2024` (read only) as per-state PMTiles at zoom 8. 2016 and 2020 values are the `__prec16` / `__prec20` files on `data/election`, row-aligned to those polygons. Packs are content-hashed per state, year, and office. The database stores thin precinct units, `unit_crosswalk` membership, and `precinct_rollup`. Those rollups are not written into `result`, so they do not replace official totals. `/api/v1/results?unit_type=precinct` reads the pack.
- Negative `votes` stay rejected (`R03_votes`). They are real negative numbers on `all-others`, not a shifted column. A file's report lists every rule with its own count (`R03_votes`, `R07_unit`, and the rest). The first rule is not used as the label for the whole file.
- Company locations at `data/companies` `c6f1cf9` are 212,439 rows and 172 brands. Every `sub_entity_id` gets an `entity` row, plus a `brand_of` relation from the location's brand. The size check uses that row count.
- Node 20.19 is enough. Vite 7 asks for 20.19 or 22.12. Nothing in v3 needs 22. `engines` is `>=20.19`. CI installs Node 20.
- 2020 and 2024 presidential state totals are not summed from counties. The shell shows 2016 states, then Pennsylvania counties.
- Senate results for 2022 and 2024 load state, county, state senate, state house, US House, and school files. `data/election` `0e058f7` removed the negative `all-others` votes, so `us_senate_2022_ushouse.csv` and `us_senate_2024_ushouse.csv` (1,023 rows each) are on the district load. Negative `votes` are still rejected.
- `v3/.cache/election`, `v3/.cache/geo`, `v3/.cache/companies`, and `v3/.cache/precinct-values` refresh when the origin data-branch commit differs from the stamped `.commit`. That commit is stored on `load_batch.git_commit`.
- `data/inst-entities` `1fde48d`: `entity_relations.csv` relation `parent` fills `entity.parent_id` (and `entity_relation`). `entity_images.csv` uses `role`, `file`, and `feed_id`. `entities.csv` `wikidata` is already `wikidata:Q…` and is not prefixed again.
- After `db:load`, and before institutions when that flag is set, each US `entity_location` is assigned to its county, state, and US House unit. The pass is slices of about 10,000 ids. Each slice is its own transaction: it builds `loc_hit`, indexes and analyzes it, and writes with set-based joins. A dropped WebSocket retries that slice once. Slices that already committed stay committed, and running the command again changes nothing when the hits are unchanged. The smallest polygon wins when a point is on a boundary. `entity_location.unit_id` is the county. The state and US House links are `entity_location_unit`. A US point that hits nothing gets the flag `no_unit_resolved`. Non-US rows stay unit-less and keep `country_code`.
- The 350 MB gate reads `pg_database_size`. A rounded bytes-per-row figure is not added on top.
- `npm run precincts -- --dry-run` prints how many precinct unit, crosswalk, and rollup rows the command would write. The unit price skips centroid and `legacy_key` (polygons stay in PMTiles; the long v2 name is not copied onto the unit). An empty crosswalk or rollup table is priced from catalog row width. It writes nothing. Precinct result facts stay out of Postgres. The load itself does not store a precinct centroid: the US House crosswalk is computed from lon/lat in that transaction only.
- `npm run db:load -- --include=institutions --dry-run` prices `origin/data/inst-entities` at run time (now `f0f1f6d`; `licence_url` values are canonical https deeds; counts are unchanged) and writes nothing. The projection is the slim row width, not `pg_total_relation_size` divided by a small live table. v2 keys and long source notes go in `entity_extra` with no extra index. Image attribution, source URL, and usage text go in `entity_image_text`. A commons URL that repeats `source_url` is stored once. State text is omitted when `state_fips` is set. Licence deeds are one `license` row. The load runs only after location assignment, and only when that projection is within 350 MB (`--allow-over-budget=institutions` overrides). A public image needs attribution. A hidden image needs attribution and a source URL; rows that have neither are skipped. No image file is downloaded. `in_county` does not change `entity.parent_id`. An unknown relation method such as `tceq_wdd_primary_county` is stored as `sourced`, with the raw token on `source_record_id`. Governments, seating, and people stay unloaded.
- When a later `load_batch` for the same file name is applied, older rows of that file with status `rejected` become `superseded`. A skipped sha does not do that. Migration `013_slim_load.sql` also marks a rejected row superseded when an applied batch for that file name is already present (the 2022/2024 sldu, sldl, and school rows). A rejected file with no applied sibling stays rejected.
- Fair-use images are not loaded (D22). A ZIP with no ZCTA returns 404 and does not call a geocoder. Future timestamps allow a 2-day skew.
- GitHub Actions only runs the v3 job. The workflow file has to live at `.github/workflows/v3.yml`.
